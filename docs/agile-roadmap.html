Hexagonal, en oraciones

El handler HTTP solo parsea la request y llama a un use case en internal/application/. El use case no conoce Postgres: habla con un port (una interfaz en internal/domain/ports.go). La implementación SQL vive en internal/infrastructure/postgres/. cmd/server/main.go es el único lugar que conecta las piezas. Por eso el SQL no va en el handler y el HTTP no va en el domain: cada capa tiene un solo trabajo.

request HTTP
    → delivery/http  (parsea query, arma JSON)
    → application    (regla de negocio)
    → port           (interfaz en domain/ports.go)
    → postgres       (SQL)
    → cmd/server     (cablea todo al arrancar)

Cómo correr local

En una terminal levantá Postgres y la API. En otra, el frontend. El healthcheck tiene que devolver {"status":"ok"}; si falta DATABASE_URL, el proceso de Go se corta al arrancar.

cp .env.example .env          # opcional; make ya tiene defaults
make db-up                    # Postgres Docker en :5435
make api                      # Go API en :8080  (otra terminal: make web → Next :3000)
curl http://localhost:8080/health

El frontend se instala con cd web && npm install && cd .. && make web y queda en http://localhost:3000. El browser pega a /api/... y Next reescribe esas llamadas a localhost:8080.

Para tests, no corras go test ./... a ciegas: entra a web/node_modules y es lento. Pedí el paquete que tocaste:

go test ./internal/application/ -count=1
go test ./cmd/server/ -count=1

Palabras que aparecen en todas las cards

  • Trim: una versión de auto, por ejemplo Corolla XEi 2.0 CVT. No es un aviso publicado.
  • Listing: un aviso concreto (precio, km, año) guardado en vehicle_listings.
  • Seed: datos de demostración insertados por migraciones SQL, con source='seed'.
  • Deal: la pregunta “¿está barato este precio?”. Se responde con GET /api/v1/trims/{id}/deal?year=&price=.

E1-101Backend3 ptsStory

Umbral mínimo de 5 listings para el deal

Contexto

El deal compara un precio tipeado contra la mediana de los avisos de esa versión y año. Con un solo aviso la mediana es ese precio, así que “15% below” no significa nada: el producto estaría mintiendo. El seed del Corolla XEi 2019 tiene 10 filas, así que un curl al API local no alcanza para probar el umbral. Por eso el test usa un fake, no Postgres.

Historia

Como comprador, no quiero un badge verde si hay menos de 5 publicaciones, para no creer un descuento inventado.

Diseño

En esta story tocás domain y application. El handler HTTP ya pinta insufficient_data: no lo toques.

Comprador carga precio
        │
        ▼
GET /api/v1/trims/{id}/deal?year=&price=
        │
        ▼
AssessDeal.Execute
        │
        ├─ Count < 5  →  status = insufficient_data
        │                (deltas null, sin banda)
        └─ Count ≥ 5  →  mediana + banda below / near / above

Glosario

  • Use case: AssessDeal.Execute es la regla de negocio. El handler solo lee year y price de la URL.
  • Mediana: el precio del medio de la muestra. Con 1 listing, la mediana es ese único precio.
  • Fake repo: en el test, un struct que implementa el port y devuelve el Count que vos pongas. No usa Postgres.

Qué hay hoy

internal/application/assess_deal.go (~línea 31)

    return ... Status: insufficient_data
}

Migración trim_aliases

Contexto

El worker hoy exige trim_id en el JSON. El operador que baja títulos de Mercado Libre no conoce nuestros IDs. Esta card no resuelve títulos: solo crea la tabla que dice “este texto crudo = este trim”. El archivo .up.sql aplica el cambio; el .down.sql lo deshace. En prod el server solo corre Up. migrations/fs.go ya embebe *.sql: no lo edites.

Historia

Como el worker futuro, necesito una tabla que diga “este texto crudo = este trim_id”.

Diseño

Solo SQL. No hay use case todavía: resolver títulos es E2-203.

trim_aliases
  source    + raw_name     → UNIQUE  (no dos filas "file" + mismo texto)
  trim_id                  → FK a trims(id)  (si el trim no existe, error 23503)
  year_from / year_to      → opcional

raw_name se guarda YA en mayúsculas, igual que va a producir
normalize.Title en E2-202. Si no, el JOIN nunca pega.

Qué hay hoy

No hay tabla. El worker exige trim_id en el JSON.

Qué tiene que quedar

migrations/006_create_trim_aliases.up.sql

CREATE TABLE trim_aliases (
    id SERIAL PRIMARY KEY,
    source TEXT NOT NULL,
    raw_name TEXT NOT NULL,
    trim_id INT NOT NULL REFERENCES trims(id),
    year_from INT,
    year_to INT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (source, raw_name)
);

INSERT INTO trim_aliases (source, raw_name, trim_id)
SELECT 'file', v.raw, t.id
FROM trims t
JOIN generations g ON g.id = t.generation_id
JOIN (VALUES
    ('TOYOTA COROLLA XEI 2.0 CVT', 'XEi 2.0 CVT'),
    ('TOYOTA COROLLA XEI 2.0', 'XEi 2.0 CVT'),
    ('COROLLA XEI 2.0 CVT', 'XEi 2.0 CVT')
) AS v(raw, trim_name)
  ON t.name = v.trim_name AND g.name = 'E210';

Down: DROP TABLE trim_aliases; Seed: 6–8 filas del XEi.
